# 3.2.1 蓝图实现方案

> 更新：2026-10-23。目标环境：Minecraft 1.21.1 / NeoForge 21.1.259 / Java 21。
> 当前代码版本：0.1.54；蓝图模块已实现，合并固定产出一张。验证结果与人工待验收范围见第 10 节。参数表：[后勤-军工.xlsx](后勤-军工.xlsx)。
> 蓝图对应原始[策划书](策划书.pdf)第 3–4 页的 3.2.1“图纸”。参考结构：[3.1 矿物资源实现方案](3.1-矿物资源-实现方案.md)。策划书保持原样。

## 1. 当前范围

本阶段已实现舰船建造图纸和装备开发图纸两个物品，包含许可存储、动态名称与悬浮说明、合并、有序扩展、奖励箱获取、制造许可查询以及两个许可收集进度。

本文命名已用于当前代码和生成资源。当前共有98个注册物品，其中蓝图物品2个；24项许可是物品组件内容，不是24个新注册物品。工作簿中蓝图相关条目标记为“已实现”，船坞与开发工厂已实现，其余设施继续保留“后续设计”。

图纸阶段不注册制造设施。后续船坞与[开发工厂](3.2.3-开发工厂-实现方案.md)已分别接入制造事务：开工预留一张、完工扣除、取消不扣，费用和产量由各设施配方定义。船坞规则见[3.2.2方案](3.2.2-船坞-实现方案.md)；弹药工厂仍未实现，不填入假定费用。

图纸不绑定玩家，可交易、赠送和搬运。不保存稀有度、技术等级或个人解锁状态。制造产物由玩家从可建造内容中选择，不进行随机建造。

## 2. 注册、数据组件与标签

### 2.1 物品注册

| 注册常量 | 物品 ID | 基础名称 | 英文名 | 最大堆叠 |
|---|---|---|---|---:|
| SHIP_BLUEPRINT | piranport:ship_blueprint | 舰船建造图纸 | Ship Blueprint | 64 |
| EQUIPMENT_BLUEPRINT | piranport:equipment_blueprint | 装备开发图纸 | Equipment Blueprint | 64 |

两个注册物品共用 `BlueprintItem` 类，由构造参数区分家族。只有物品和全部组件一致的图纸才能直接堆叠。不同许可集合需要通过合并配方组合，不能在拖放或漏斗搬运时自动取并集。

创造栏提供六种有效示例，各自包含一个子类的全部许可。常规物品继续自动遍历注册项，图纸单独输出带组件示例，不展示没有许可的默认物品。图纸模型暂复用原版地图和知识之书图标，正式美术待替换。

### 2.2 许可数据组件

组件 ID 为 `piranport:blueprint_content`，值类型为不可变 `BlueprintContent`。

- 保存具体许可 ID 的集合，使用稳定字符串 ID，不保存枚举序号。
- 内部不可变，序列化采用去重、固定排序的列表，确保顺序不影响相等性和堆叠。
- 家族由物品 ID 决定，子类由许可定义推导，不重复保存家族或子类字段。
- 数量只使用 `ItemStack` 的数量，不在组件中重复保存，也不按许可分别保存使用次数。
- 提供持久化 Codec 和网络 StreamCodec；使用现有 `ModDataComponents` 注册入口。
- 所有创建入口复用合法性校验，不能混入另一家族的许可。

示例：16 张许可为 `{战列、驱逐}` 的舰船图纸，表示 16 张图纸每张都可以用于战列或驱逐制造。它不表示分别拥有若干张战列图纸和若干张驱逐图纸。

无组件、空许可集合、家族冲突和未知许可都不能参与制造、合并或扩展。能够读取的未知 ID 保留原始数据，不能静默删除后复制，也不能把缺失组件解释为全部许可。语法解码与语义合法性校验分开，避免未来许可 ID 暂时不可识别时直接丢弃整个物品。持久化和网络编解码均限制最多 128 项，后续增加类型时同步扩展与兼容读取。

组件中不加入所有者 UUID、随机唯一标识或复制代数。尤其不能通过加入 UUID 的方式阻止两张奖励图纸堆叠。

任何未知许可均使图纸整体无效，原始 ID 仅按通用数据规则保留，不提供制造权限；没有专门针对已移除舰种的迁移、转换或兼容分支。

## 4. 显示、堆叠与重命名

### 4.1 动态名称

只包含一个子类时按子类命名，跨子类时显示家族总称。只包含某子类的一种许可，也按子类命名。装备家族使用“子类名 + 图纸”；舰船家族的分类名仅为“大型”“中型”“小型”，但物品显示名称使用“子类名 + 船图纸”，即“大型船图纸”“中型船图纸”“小型船图纸”。悬浮说明的分组标题仍省略“船”字。

| 许可示例 | 名称 |
|---|---|
| 战列 | 大型船图纸 |
| 战列、航母 | 大型船图纸 |
| 重巡、轻巡 | 中型船图纸 |
| 驱逐、潜艇 | 小型船图纸 |
| 战列、驱逐 | 舰船建造图纸 |
| 雷达、声呐 | 设备图纸 |
| 主炮、雷达 | 装备开发图纸 |

“设备图纸”是装备家族中“设备”子类的名称；“装备开发图纸”是跨子类名称。名称通过中英文语言资源实时生成，不把本地化文本写入许可组件。

### 4.2 悬浮说明

悬浮说明只列实际可建造类型，中文使用简称，可按“大型”“中型”“小型”等子类名分组；不显示“制造时消耗”“可与同类图纸合并”等操作提示，也不显示稀有度或技术等级。

归属行可见性沿用原版：创造界面等场合已有“皮兰港”归属行时，仅将原组件移至许可分组说明下方；没有原版归属行时不补加。通用事件不隐藏、去重或重新着色，也不管理其他模组添加的归属提示，不写入物品组件。以下示例为许可内容，原版归属行仅在其正常显示的场合跟随于下方。

例如 `{战列、战巡、驱逐}`：

```text
大型：战列、战巡
小型：驱逐
```

例如 `{主炮、雷达、声呐}`：

```text
武器：主炮
设备：雷达、声呐
```

不列未许可的类型，不将部分子类许可写成“可建造全部大型舰船”。无需右键 GUI。

### 4.3 名称与其他组件继承

- 扩展：保留原图纸自定义名称，动态名称仍由许可计算。
- 合并：全部输入具有相同自定义名称时保留；名称不同，或命名图纸与未命名图纸混合时，恢复动态名称。
- 输入顺序不影响许可集合、输出数量和名称结算。
- 扩展通过原图的完整副本保留全部组件。合并比较许可和自定义名称以外的组件补丁，必须全部一致；一致则完整继承，不一致则配方不匹配，避免丢弃附加数据。

## 5. 合并与扩展配方

### 5.1 合并

配方 ID：`piranport:blueprint_merge`。动态无序配方，使用原版 crafting 配方类型，兼容背包 2×2、工作台 3×3 和原版合成器。

1. 非空槽位必须为 2–4 格，每格均为合法图纸，全部属于同一家族。
2. 不允许其他额外材料，不限制槽内原有总堆叠数量。
3. 每次每格消耗一张，固定产出一张新图纸；许可为所有输入的并集。
4. 相同许可允许合并，重叠许可去重；即使全部输入内容相同，也消耗每格一张、只产出一张。跨子类合并允许，跨家族合并拒绝。
5. 不产生额外原图余留，不提供拆分许可的逆配方。

| 单次输入 | 输出 |
|---|---|
| 1张 `{战列}` + 1张 `{驱逐}` | 1张 `{战列、驱逐}` |
| 1张 `{战列、战巡}` + 1张 `{战巡、航母}` | 1张 `{战列、战巡、航母}` |
| 2–4格均为 `{战列}`，每格各取1张 | 1张 `{战列}`，相同许可也只产出一张 |
| 4格同家族图纸，各取1张 | 1张，许可取四格并集 |
| 2格各放64张图纸 | 单次输出1张，各输入格剩63张 |
| 1格或5格图纸 | 不匹配 |

输出数量不取决于参与格数或槽内堆叠总量。Shift 合成由原版重复执行；每次仍遵守每格扣一张、固定产出一张。合并2、3、4张的数量净变化分别为−1、−2、−3张。

产出的一张新图纸获得许可并集，不维持各许可原来的数量份额。相同许可也按消耗式合并结算，不退还原图纸。

### 5.2 有序扩展

配方 ID：`piranport:blueprint_expand`。动态有序配方，固定 3×3：

| #c:papers | #c:dyes/blue | #c:papers |
|---|---|---|
| #c:papers | 原图纸 | #c:papers |
| #c:papers | #c:papers | #c:papers |

每次消耗 1 张原图纸、1 个蓝色染料和 7 张纸，产出 8 张同家族、完整继承许可的图纸，净增加 7 张。原图不返还。两个家族复用实现逻辑，不允许空白或异常图纸扩展。

只接受表中位置，不允许旋转或上下翻转；左右镜像因布局对称不形成另一种配方。七格纸逐格使用标签匹配。

### 5.3 结算与自动化

匹配、输出预览、许可查询和 `assemble` 不改变输入；实际扣料使用标准合成流程。每次创建独立输出对象，不修改配方共享结果，不在合成事件中额外扣图纸或额外生成产物。

原版合成器无需玩家所有权或个人解锁记录。每轮扩展消耗原图并输出 8 张，装置自行从输出回送 1 张到中心格，剩余 7 张为净产出；配方不得通过余留物再返还一张。供料顺序、回送和红石线路属于原版装置操作。

配方使用原版 `CustomRecipe` / `SimpleCraftingRecipeSerializer` 路径，属于特殊合成配方，未添加配方书或 JEI 的代表性展示适配。工作台和合成器实际匹配、内容继承及扣料已有回归；世界内动态展示另行验收，不能据主菜单加载成功认定配方界面可见。

## 6. 奖励箱与随机内容

### 6.1 投放范围和数量

| 来源 | 战利品表 | 0张 | 1张 | 2张 | 平均张数 |
|---|---|---:|---:|---:|---:|
| 沉船财宝箱 | minecraft:chests/shipwreck_treasure | 25% | 50% | 25% | 1.0 |
| 埋藏宝藏 | minecraft:chests/buried_treasure | 0% | 50% | 50% | 1.5 |

不向 `minecraft:chests/shipwreck_map` 和 `minecraft:chests/shipwreck_supply` 添加图纸。藏宝图物品不直接给予图纸，奖励位于其指向的埋藏宝藏箱。后续自建结构另行接入奖励表。

数量分布可用两个独立抽取实现：沉船两次各 50% 命中；埋藏宝藏一次必定命中、另一次 50% 命中。每次命中都独立生成内容。

### 6.2 两张分别生成，不主动合并

获得两张时分别随机许可，各自产生一个数量为 1 的独立 `ItemStack`。即使家族、许可和其他组件完全相同，也保留为两个生成结果，不主动堆叠、压缩或去重，不把一次内容抽取后设置 `count=2`。

这项要求约束奖励生成流程，不改变图纸原有的堆叠能力。原版后续容器处理、拾取或玩家背包操作仍可自然堆叠；不为维持分开状态增加随机组件或唯一标识，也不承诺对其他模组后续处理强制拆堆。

### 6.3 单张内容

每张图纸只选择一个家族下的一个子类，再取得该子类的非空许可子集。两张之间可以出现不同家族、不同子类，也可以完全相同。随机性只影响奖励内容，制造时由玩家选定产物。

单子类候选数量：

- 舰船：`(2^3−1) + (2^3−1) + (2^3−1) = 21`。
- 装备：`(2^4−1) + (2^7−1) + (2^4−1) = 157`。
- 合计178种合法奖励内容；跨子类组合由合并产生，不列入自然奖励候选。

**当前实现的内容分布：** 两个家族等概率；各家族三个子类等概率；子类内先等概率选择许可数量 `1..m`，再等概率选取该数量的不重复组合。不把178个候选直接整体等权抽取，以免组合更多的子类占据额外概率。分布保存在战利品数据中，可由数据包调整，不是图纸上的稀有度属性。

候选由 `BlueprintData` 数据生成枚举，用普通战利品条目和组件函数赋值。家族、子类、数量、组合通过内联子表分层表达；`blueprints/content` 保存完整内容树，另有 `blueprints/shipwreck`、`blueprints/buried_treasure` 两张奖励表。

### 6.4 接入和旧箱子

使用当前 NeoForge 内置 `neoforge:add_table`，按目标战利品表 ID 追加本模组奖励表，不覆盖原版整表。`global_loot_modifiers.json` 使用追加方式，`replace=false`。

- `data/neoforge/loot_modifiers/global_loot_modifiers.json`。
- `data/piranport/loot_modifiers/blueprints_*.json`。
- `data/piranport/loot_table/blueprints/*.json`。

新生成箱子，以及仍保留战利品表、尚未结算的旧箱子，可使用新规则。已经结算的箱子不补发，不扫描或重写已有箱子；“玩家未打开过”不必然等于“尚未结算”。

## 7. 制造许可接口

由 `BlueprintRules` 提供纯查询，先验证物品家族及组件合法性，再判断许可。查询不扣图纸、不写入存档，也不修改个人进度。

| 接口 | 含义 | 用途 |
|---|---|---|
| allowsType(stack, type) | 包含指定具体许可 | 确认某个产物能否制造 |
| allowsSubclass(stack, subclass) | 该子类至少一种许可被覆盖 | 界面分类是否有可建造内容 |
| coversSubclass(stack, subclass) | 该子类全部许可被覆盖 | 明确判断完整覆盖 |
| getAllowedTypes(stack, subclass) | 返回该子类实际许可集合 | 过滤可建造产物与显示 |

例如 `{战列、驱逐}`：`allowsSubclass(大型)=true`，`coversSubclass(大型)=false`，`allowsType(航母)=false`。子类“有所覆盖”不能直接作为允许制造整个子类全部产物的条件。

不能仅用普通物品 `Ingredient` 判断，因为需要查询组件中的许可；也不能以整个许可组件相等代替“包含某项”。后续制造配方声明所需具体许可，最终执行前再次验证投入图纸。

制造每件产物固定消耗 1 张，不新增可配置的图纸费用字段。批量 N 件对应 N 张，不允许输出 N 件却只消耗一张。船坞开工扣材料与燃油、在槽内预留一张图纸，完工才扣图纸；取消释放预留并退回净投入。任务快照与暂停规则见 [船坞方案](3.2.2-船坞-实现方案.md)。图纸查询接口本身仍不实施扣料事务。

## 8. 许可收集进度

只设置两个进度，不设置跨家族总体进度：

| 目标 | 目标许可数 | 进度 ID |
|---|---:|---|
| 取得所有舰船类型许可 | 9 | piranport:blueprints/all_ship_types |
| 取得所有装备类型许可 | 15 | piranport:blueprints/all_equipment_types |

采用曾经获得的累计方式，每项许可分别记录。复合图纸可以同时满足多项，不要求同时持有全部图纸。使用、赠送、丢失和死亡不会撤回已经满足的条件，跨会话保留。

合法图纸实际进入玩家直接物品栏或副手后计入；拾取、交易、制造、赠送得到的图纸均可。只打开箱子、悬浮查看或让自动合成器产出不计给某个玩家，实际取得后才累计。不递归扫描箱子、潜影盒或其他嵌套容器。

借用其他玩家的完整图纸也可以完成收集。这个目标记录获得许可的经历，不限制来源，不绑定图纸，不授予制造权限。

复用原版 `inventory_changed` 和 `piranport:blueprint_permission` 物品子判定，每个目标许可一个 criterion，同家族所有条件以 AND 完成。原版进度数据负责持久化，无需另存一套玩家许可集合。`BlueprintCollectionEvents` 登录时补判直接物品栏和副手，避免新增进度后现有物品漏判；不做每 tick 全背包扫描。

异常图纸不计入条件；两个进度不串项。新增许可后的目标扩展另行定义；内部旧存档不迁移，正常进度不无声撤回。进度撤销仍可由原版管理命令控制。
