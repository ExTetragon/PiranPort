# 3.1 矿物资源修复说明

> 日期：2026-10-22。目标环境：Minecraft 1.21.1 / NeoForge 21.1.259 / Java 21。
> 本文对应审查中的问题 1–10 及全部遗漏项。实现规则同时同步到实现方案、测试清单、README 和两份 xlsx。
> 策划书保持原始版本，实施校正及当前测试源码状态见 [开发日志](开发日志.md)。下文容量及运行结果为 2026-10-22 修复阶段的历史记录。当前默认容量已调整为单桶 16000 mB、双桶 32000 mB，并增加容量和放置连接策略配置；当前规则与降容兼容见[实现方案 4.6](3.1-矿物资源-实现方案.md#46-公共配置与放置策略)。

## 1. 燃料桶的数据与连接模型

旧实现把全部流体存进动态 master 储罐，每次查询都从邻居临时推导 master。
这使第三个桶、区块加载次序、切轴及管道缓存都能改变“当前储罐”的含义。
新实现保存明确的成对伙伴坐标，每格各自保存流体，由固定身份的 SharedHandler 把两格作为一个逻辑储罐暴露。

正常单格 32000 mB，两格共享 64000 mB。master 决定优先填充顺序；它不再独占持久化数据。
所有转移先检查流体及组件是否兼容、总量是否可容纳，然后使用 copyWithAmount 分配，保留流体元数据。

### 1.1 对应问题 1：空流体保存

saveAdditional 改用 FluidStack.saveOptional。空桶、空 slave 和排空后的桶都能保存；loadAdditional 读取可选 Fluid 字段。
旧版调用 save 会抛异常，Minecraft 跳过该方块实体的保存，新版消除了这条异常路径。

### 1.2 对应问题 2：放置丢油或覆盖邻桶

移除 FuelBarrelItem.place 中“先调用 super.place、再读手中物品”的实现。
vanilla 在消耗 ItemStack 之前调用 BlockEntity.applyImplicitComponents，此时恢复本格内容；之后 setPlacedBy 再建立共享关系。
带油物品既不会因数量减为零读不到组件，也不会把邻桶 master 的内容直接替换。

### 1.3 对应问题 3：没有保存变更

FluidTank.onContentsChanged 回调所属方块实体的 contentsChanged，实际 fill/drain 均执行 setChanged。
同时通知本格和伙伴位置更新比较器。数据恢复、重分配和连接变化也走相应通知。
GameTest 会先清除区块的 unsaved 标记，再验证 fill 和 drain 分别把它重新标记为需要保存。

### 1.4 对应问题 4：混油隐藏或覆盖

建立配对前要求两格为空，或流体类型与数据组件兼容。不同油品不连接；同种油品但元数据不同也不连接。
不再出现 slave 中藏着燃油、对外接口却返回 master 原油的状态。

### 1.5 对应问题 6：三连、移除与容量不一致

已有配对持久保存，不会因第三格出现而解散。第三格只能与其他未配对的兼容邻桶建立新的一对。
onLoad、邻居变化和轴向变化会安排连接校验；查询不强制加载相邻区块。
容量从当前有效伙伴关系计算，不再把旧的 64000 容量原样永久沿用。

玩家破坏在 playerWillDestroy 阶段先结算：留下的桶优先装满，多余部分随被挖桶掉落。例如 40000 mB → 剩余 32000 + 掉落 8000。
创造模式仍不掉落。非玩家移除只断开关系，各格保留本格份额，因为爆炸/程序移除的战利品可能已在 onRemove 之前生成，不能在此时再搬油。

### 1.6 对应问题 7：旧管道引用失效

每个方块实体始终返回同一个 SharedHandler。该对象每次操作时重新解析伙伴，配对变化无需替换对外对象。
两格关系变化时仍显式 invalidateCapabilities，使采用 NeoForge 缓存的外部模组及时收到通知。
移除方块实体后，旧代理不再可读写；拆分后，缓存代理只操作自己所属的那一格。

### 1.7 对应问题 8：比较器无输出

覆写 hasAnalogOutputSignal 返回 true；输出 floor(15 × 当前存量 / 当前容量)，上限 15。
容量和内容变化均更新邻近比较器，空、半满、满对应 0、7、15。

### 1.8 实际运行额外发现：数据组件必须不可变

首轮 GameTest 中四个涉及物品组件/掉落的用例触发 Minecraft 检查：数据组件必须实现相等比较和哈希，并保持不可变。
原来的 DataComponentType<FluidStack> 不符合这个约束。
改为 NeoForge 提供的 SimpleFluidContent，使用官方 CODEC / STREAM_CODEC；恢复时取得可变副本，掉落时复制成不可变内容。
组件 id 仍为 piranport:fluid_content。非空内容的持久化结构与旧 FluidStack 编码兼容。

### 1.9 旧存档迁移

本节记录历史修复背景。自 0.1.75 起，内部测试不维护旧格式迁移；已移除存储版本标记、缺字段默认兼容和专用旧格式测试。当前配置降容守恒仍保留，规则以[实现方案](3.1-矿物资源-实现方案.md#44-当前格式存档与配置降容)为准。

新版写 StorageVersion=2，但仍读取旧 Fluid 和 PlaceOrder。
旧 master 中仍存在的 64000 mB 先完整读入，重新配对后分成两份 32000。伙伴尚未加载或不存在时保留超额存量，只允许抽出，禁止继续填充。
这避免修复过程再次截断数据；此前已经丢失、从未保存的内容无法恢复。

## 2. 对应问题 5：固体方块掉落

为矾土块、铝块、钢块生成自身掉落表，避免合成储存块后挖掘丢失材料。
燃料桶改用正常战利品表和 minecraft:copy_components，复制本格 fluid_content；移除旧 noLootTable 和额外手动生成掉落的代码。

ModDataGenerators 接入 GatherDataEvent，生成 4 张战利品表和 7 个矿石/储存块物品标签。
生成资源保存在 src/generated/resources 并纳入版本控制；手写资源保留在 src/main/resources，无同名重复文件。

## 3. 对应问题 9：油湖群系及半径

旧版在全部含油群系加入砂岩、红砂岩、石头三种特征，导致材料混用和三倍尝试。
新版拆分为沙漠、恶地系、热带草原系各自的地表/地下修饰器，每个群系只引用对应材料。

- 沙漠：砂岩；恶地：红砂岩；热带草原：石头。
- 地表半径 4–8，稀有度抽样 1/150；地下使用独立 configured feature，半径 4–6，抽样 1/50。
- 所有 placed feature 加入 biome placement filter，阻止采样位置跑进未配置该特征的邻近群系。
- 稀有度是尝试概率，地形验证可能放弃，因此实际成功数量更低。

## 4. 对应问题 10：油湖安全与形态

油湖先在内存中计算全部油体、侧壁/底壳和上方清理坐标，再检查整个范围，验证通过前不改动世界。

- 所有写入点必须在世界高度与当前生成区块的可写范围内。
- 油体及密封壳只能替换天然地形白名单，不包括容器、建筑材料、基岩和流体。
- 湖底紧邻最后一层油，修正原来的多减一格；侧面也形成连续壳。
- 侧壁开放或底面无支撑时整次放弃，不残留半截湖。
- 湖面略低于中心地面，可清理少量天然起伏，GameTest 验证一格缓坡仍能生成；不强行挖穿山体。
- 任一受保护方块或方块实体存在时，保持原地形和容器内容不变。

新增 oil_lake_replaceable 方块标签；数据包可以扩展允许的天然地形。

## 6. 设计资料同步

策划书.pdf 已恢复为修改前的原始 5 页，不再追加或改写内容。原先附页中的硝土掉落、燃料桶容量/组合、世界生成、资源完整性及验证说明，统一迁入 [开发日志](开发日志.md)的“3.1 实施校正”一节；后续差异和开发历史也记录于该文件。

### 可重复命令

在项目目录的 PowerShell 中：

~~~powershell
$env:JAVA_HOME = 'C:\Program Files\Java\jdk-21'
.\gradlew.bat runData
.\gradlew.bat build
.\gradlew.bat runGameTestServer
python tools/verify_resources.py
~~~

默认构建输出被占用时，为三个 Gradle 命令加入 -PbuildOutput=build/verification。
当前 src/gameTest 为空且被忽略；上述 runGameTestServer 只有恢复完整测试源码及结构模板后才能重现 17 项回归，不能把空源集或旧输出运行计为新的通过。
本次验证使用本机已有缓存和独立输出目录，不停止用户的 IDE 或已有游戏进程。
