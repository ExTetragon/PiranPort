# 2.1.1 舰装核心实现方案

> 更新：2026-10-24。目标环境：Minecraft 1.21.1 / NeoForge 21.1.259 / Java 21。
> 当前代码版本：0.1.65。舰装核心物品层、通用舰种/船型、逐舰图标及熟练度基础接口已实现；表内参数仍为首轮调试基线。验证记录见第 14.3 节，人工待验收范围保持独立。
> 参数及实现状态：[舰装-舰装核心.xlsx](舰装-舰装核心.xlsx)。原始依据：[策划书](策划书.pdf)第 3–4 页的 2.1.1；蓝图衔接见[蓝图实现方案](3.2.1-蓝图-实现方案.md)。

## 1. 范围与交付边界

舰装核心是保存舰船身份、熟练度、装配内容、弹药、燃油与仓库物品的独立物品。核心自身提供查询、存储与属性汇总能力，后续舰装栏和舰娘状态通过这些接口访问核心。

本阶段实现一个注册物品、十个舰船定义、共用舰种与船型枚举、逐舰独立图标、熟练度初始化/保存/读取/上限/显示及预留读写接口、四类物品空间、一个燃油储罐、名称和 Shift 悬浮说明、掉落物防护、有效创造栏示例，以及对应的自动回归。

舰娘状态、玩家专用舰装栏、GUI、HUD、变身、玩家属性应用、水面或水下移动、燃油自动消耗、装备运行与发射、飞机实体、船坞及制造事务均属后续范围。物品层不新增玩家死亡搬运逻辑，不实现工作台替代配方，也不向末地城或深海奖励箱追加核心。

熟练度的具体增长方案与收益暂缓，仅为后续舰娘状态和收益模块预留接口；本阶段不设增长速率、培养时长、增长曲线、计时或挂机规则，也不接入自动增长与属性收益。

核心已注册，创造栏提供十个有效身份示例，普通玩家本阶段没有内部物品整理界面；分类存储通过领域接口、物品能力和测试访问。手持核心与现有燃料桶已通过既有路径双向转移燃油。

### 2.1 逐舰图标与资源映射

根模型为 `assets/piranport/models/item/rigging_core.json`。客户端使用 Minecraft 1.21.1 的自定义物品模型属性与 `overrides`，读取身份中的舰名 ID，选择 `assets/piranport/models/item/rigging_core/<舰名路径>.json`，子模型引用 `assets/piranport/textures/item/rigging_core/<舰名路径>.png`。

舰名路径直接对应第 4.1 节舰名 ID 的路径部分，例如列克星敦为 `lexington_cv2`，贴图资源标识为 `piranport:item/rigging_core/lexington_cv2`。十艘舰船各有独立子模型和贴图；舰名到模型的选择只在客户端表达，不在物品中重复保存模型编号、纹理路径或可变的枚举序号。

占位图采用统一核心底形、每舰不同徽记和配色，确保同舰种的不同舰船也可区分；正式美术沿用相同资源路径替换。图标依据真实身份，铁砧改名、熟练度和内部装配变化均不改变图标。背包、手持、掉落物、展示框和创造栏使用同一身份选择规则，模组创造栏显示列克星敦子模型。

无身份、未知舰名或舰名与舰种不一致时回退通用图标，保留原始身份、熟练度与内部内容。选择逻辑不依赖当前玩家或世界对象，保证创造栏等无实体上下文的显示正常；所有客户端注册放在客户端加载路径。已知舰船的模型、贴图缺失由静态资源与客户端检查发现。

## 3. 共用舰种与船型

### 3.1 通用定义

提取通用 `ShipType`、`ShipSize`，核心与蓝图共同引用。通用定义放在 `domain/ship/`，不依赖具体蓝图或舰装实现；其他跨系统共用的领域模型按需放入 `domain/` 的对应领域子包。

`ShipType` 负责九种舰种的稳定 ID、译名与所属船型；`ShipSize` 负责三种船型的稳定 ID、译名及本阶段容量。蓝图现有的混合许可目录还包括装备，不能整体改名为 `ShipType`。

蓝图适配层引用通用定义，移除其独立维护的舰种名称、ID 和舰种到船型关系。适配层可以保留现有查询入口，不能继续维护第二套舰种映射。所有已有许可及子类 ID 保持原样，旧图纸的有效性、合并、奖励与收集条件不改变。

### 3.2 身份组件

组件 ID 为 `piranport:rigging_identity`。不可变值保存两个稳定 ID：舰名 ID、舰种 ID。船型从已识别的通用舰种推导，不在核心中重复保存。

舰名 ID 与舰种 ID 的命名空间均为 `piranport`，二者含义独立。序列化使用字符串 ID，不保存枚举序号或本地化文本。舰名目录提供对应舰种、名称与基础属性。

创建接口只接收舰名 ID，从舰船定义一次性写入合法身份，不能自由拼接某舰名与另一舰种。读取时核对舰船定义存在、舰种可识别以及两者一致。正常玩法没有更换身份的接口；铁砧、存取物品、加油与核心转赠均不改变身份。

持久化与网络解码保留语法合法的未知 ID，语义校验另行执行，避免舰船定义暂时缺失时导致整个物品解码丢失。查询缺失身份时不自动抽取舰名或初始化组件。

首批共十艘、七种舰种。轻母与重炮保留通用类型和容量规则，本阶段不补造舰名或示例。

舰名定义采用集中、不可变的目录，保存舰名 ID、中英文名称对应的翻译键、通用舰种以及三项基础属性。后续确有数据包扩展需求时再设计目录加载和同步；本阶段不提前加入动态注册与热重载系统。

基础属性从舰名定义查询，不在每枚核心中保存制造时快照。以后调整某舰定义的数值，已有核心采用新值；同一舰名的舰种关系保持稳定；内部测试改变该结构时使用新存档，不增加旧身份迁移。

## 6. 收纳类别与嵌套限制

| 区域 | 接收规则 | 单槽上限 |
|---|---|---:|
| 武器栏 | `piranport:weapons` 或 `piranport:aircraft` 物品标签 | 1 |
| 设备栏 | `piranport:devices` 物品标签 | 普通装备1；快修64、损管16 |
| 弹药库 | `piranport:ammunition` 物品标签 | 物品自身堆叠上限 |
| 仓库 | 普通物品与允许的便携容器，拒绝核心及内含核心的容器 | 物品自身堆叠上限 |

同一区域内各格规则相同。舰名、舰种、舰船规模不构成额外的装备硬限制；小型船也能收纳重型主炮。适配、超重及相关负面效果留待舰娘状态处理。

标签定义在`data/piranport/tags/item/`，默认列入已实现的本模组武器、设备、飞机和弹药。快修、损管同时具有`equipment_consumables`标签，在设备栏按自身上限堆叠，不提供舰娘属性；其余装配每格1件。图纸拥有制造许可，不因此被装备槽接收。物品规则见[装备方案](2.2-装备-初步开发方案.md)。

标签控制收纳资格，属性与功能由装备定义或接口提供。其他模组物品通过数据包加入标签后可以收纳，但不会自动获得发射行为或把原版攻击伤害转换为舰装属性。

### 6.1 潜影盒与收纳袋

仓库允许空或有内容的潜影盒、收纳袋，但拒绝其中直接或经受支持容器间接包含核心的物品。直接插入另一枚核心同样拒绝，包含未初始化核心时也拒绝。

核心本身允许放入潜影盒和收纳袋。检查发生在核心接收物品时，不为外层容器增加防护或生命周期控制，也不逐 tick 扫描玩家背包。首版识别原版容器内容与收纳袋内容组件；第三方容器按其公开的内容接口增加适配，不承诺识别不公开内容的容器。

NeoForge 默认容器过滤会拒绝潜影盒，因此需要按本规则显式放行后检查内容，不能直接照搬默认 `canFitInsideContainerItems` 结果作为仓库全部规则。

实际检查通过 `RiggingSlotRules.containsCore` 和原版容器/收纳袋组件执行；第三方公开内容可通过 `registerContainerAdapter` 适配。单次扫描最多 16384 个节点、64 层，超出时保守拒绝本次插入，不删除既有数据。扫描不查询会产生副作用的第三方写入能力。

### 6.2 统一写入校验

`RiggingSlotRules` 集中判断区域、类别与嵌套。物品处理器的 `isItemValid` 检查类别，`insertItem` 处理容量、组件相等及剩余数量，`setStackInSlot` 同样检查类别和数量。未来 GUI 复用这套规则，服务器执行最终校验。

模拟插入和抽取不改变输入、核心组件或身份。无效插入原样返回，部分插入返回准确余量，清空槽位始终可执行。读取返回副本，不能通过修改查询结果绕过写回。

标签修改或参数调整后，已保存内容不自动删除；新增插入按当前规则执行。超出新槽位范围的旧内容保留，并提供受限取出路径，不能在读档、复制或一般写入时静默截断。

## 7. 数据组件与存储接口

| 组件 ID | 值类型 | 用途 |
|---|---|---|
| `piranport:rigging_identity` | 不可变 `RiggingIdentity` | 舰名 ID、舰种 ID |
| `piranport:rigging_proficiency` | 不可变 `RiggingProficiency` | 每枚核心独立保存的整数熟练度，范围 0–200 |
| `piranport:rigging_weapons` | `ItemContainerContents` | 武器栏 |
| `piranport:rigging_equipment` | `ItemContainerContents` | 设备栏 |
| `piranport:rigging_ammunition` | `ItemContainerContents` | 弹药库 |
| `piranport:rigging_cargo` | `ItemContainerContents` | 仓库 |
| `piranport:fluid_content` | 既有不可变 `SimpleFluidContent` | 核心燃料库 |

新增组件通过 `ModDataComponents` 注册，提供持久化 Codec 和网络 StreamCodec。物品空间复用原版容器内容值，燃料复用项目既有不可变流体组件，不将可变 `ItemStackHandler` 或 `FluidTank` 本身保存为组件。

修改以读副本、完成校验、替换不可变组件的方式写回。仅替换发生变化的组件，保留核心自定义名称、附魔及其他无关组件。复制核心后，各份物品内容修改独立；物品与流体的组件在存取中完整保留。

物品能力由 `ComponentItemHandler` 的区域处理器及统一视图适配，流体能力由受限的 `IFluidHandlerItem` 适配。处理器每次读取当前组件，不缓存会过期的内容快照。

公开读取入口包括身份、船型、熟练度、基础属性、最终属性、各区域处理器及燃料处理器。语义异常通过明确状态或可选返回值表达，不能把缺失定义解释为零属性的合法舰船。

### 7.1 异常身份与恢复

无身份、未知舰名、未知舰种，以及舰名和舰种不匹配均不作为正常可用核心。已保存的原始身份和内部内容继续保留，不补发默认身份，也不以最大船型授予容量。

语义异常核心拒绝新增物品与燃油，提供基于现存已解码内容的受限取出、抽取接口，避免内容被永久封死。后续恢复定义时重新校验即可恢复正常访问，无需制造新核心替换旧核心。

未知身份处理不影响名称颜色、物品防护与永久存续。身份无效不能作为降低掉落物保护的条件。

### 7.2 熟练度基础数据与预留接口

熟练度英文采用 Proficiency，组件 `piranport:rigging_proficiency` 保存不可变的整数值，初始为 `0`，最低为 `0`，最高为 `200`。熟练度属于每枚核心的可变数据，不放入舰船定义或身份组件；同舰名的不同核心独立保存，转赠时随物品保留，不绑定玩家。

工厂创建与创造栏示例的熟练度均初始化为 `0`。缺少组件的旧核心按 `0` 读取，查询本身不补写组件。保存、网络往返、复制、改名、普通存取、重载和转移均保留现有数值；各副本后续修改独立。舰船定义暂时缺失或身份不一致时保留熟练度，不因身份异常清零。

物品层集中提供 `getProficiency`、`setProficiency` 和 `addProficiency` 入口。读取为纯查询；直接设置只接受 0–200 的整数，越界时拒绝修改；增加入口只接受非负增量，达到 200 时饱和，返回实际增加值，并避免大增量整数溢出。无变化时不重复替换组件，所有写入保留身份、名称、库存、燃油及其他无关组件。写入校验目标为核心物品，游戏调用由服务器执行。

后续成长以玩家穿戴该核心并处于舰娘状态的时间为方向，具体增长方案确定后由成长模块调用写入接口，收益模块读取当前数值。本阶段只交付初始化、保存、读取、上限约束、Shift 显示和这些接口；不挂接穿戴计时或自动增长事件，不预设训练时间存档字段，也不确定挂机、离线、切换、死亡等计时策略。增长速率、练满时长、曲线、零头时间累计和具体收益均为待讨论项。

## 8. 属性汇总

统一规则为 `最终属性 = 舰名基础属性 + 所有已装配装备的属性修正之和`。耐久、装甲、航速分别计算，负值参与加减，不引入百分比乘区或新的永久强化数据。

熟练度本阶段仅保存和显示，不参与耐久、装甲、航速或其他收益计算；收益接口预留给后续设计。

汇总只读取武器栏、设备栏中的装配内容，飞机按所在武器栏参与；弹药库、仓库中的备用物品不参与。耐久装备每格最多一件，按实际装配逐件累计；快修、损管不实现属性接口，不参与汇总。具体唯一或互斥装备待其定义时处理。

三项结果由 `RiggingStatsCalculator` 一次汇总后供显示和后续系统调用，不另存结果组件。缺少舰装属性定义的标签兼容物品不贡献这三项数值。查询不扣油、不消耗弹药、不修改装备，也不临时把属性施加给玩家。

悬浮面板表示核心及其装配共同提供的属性，与持有者无关。耐久不是当前血量，核心也不保存玩家受伤状态。当前不执行玩家属性钳制、移动或临时战斗效果；这些规则由后续舰娘状态系统确定。

内部计算保留数值精度，显示阶段再格式化。航速显示两位小数，耐久与装甲按实际数值显示，避免每件装备先舍入后累计。

## 9. 燃油储存与交互

核心燃料库只接收本模组燃油，拒绝原油、水等其他流体。流体类型过滤属于核心处理器，不能沿用既有通用燃料桶接收任意流体的默认行为。

容量按船型表确定，支持部分灌入与抽取。合并流体同时比较种类和组件，执行前检查可接收量，保存时保留组件。`SIMULATE` 不修改任何物品或流体；空罐使用可选流体编码，抽空不销毁核心或改变其他组件。

降容时保留已存超额燃油，停止继续灌入并允许抽取，不在载入时截断。身份语义异常时按恢复接口抽取。

注册 `Capabilities.FluidHandler.ITEM` 后，手持核心与现有燃料桶通过既有 `FluidUtil` 路径转移燃油。回归必须检查真实交互方向、容量不足、抽空、组件保留与其他核心内容守恒。本阶段不新增 GUI 加油入口，也不自动消耗燃油。

统一物品能力并不意味着原版漏斗能访问核心内部空间。后续自动化必须通过支持物品能力的实际接口接入。

## 10. 名称与悬浮说明

默认标题为本地化舰名，颜色固定为 Logo 主蓝色 `#6699FF`，不通过原版 `RARE` 的青色代替。铁砧自定义名称优先显示，仍使用相同蓝色；清除自定义名称后恢复舰名。自定义名称不改变身份。

未按 Shift 时，模组只追加灰色“舰装核心”一行；英文为 Rigging Core。灰色采用原版 `GRAY`（`#AAAAAA`），不附加“按 Shift 查看”等操作提示。

所有物品（含核心）的归属行可见性沿用原版：原版创造界面等场合已追加“皮兰港”归属行时，将现有行放到本模组说明下方；生存物品栏等原版不追加归属行的场合也不补加。具体可见场景由原版决定，不单独按玩家游戏模式判断。

`client/event/ModTooltipEvents` 仅在已有 `itemGroup.piranport.main` 行位于本模组说明上方时移动原组件。它不创建、删除、去重或重新着色，不为核心设置例外，也不处理其他模组添加的归属提示；已有位置正确或没有本模组说明时不改顺序。

按 Shift 时，灰色通称消失，改为以下详情：

```text
<真实舰名>
大型·航母·U国
熟练度：<当前值> / 200
耐久：<所有装配计算后的数值>
装甲：<所有装配计算后的数值>
航速：<所有装配计算后的数值> 格/秒
燃油：<当前量> / 128000 mB
武器栏：<占用> / 6 格
设备栏：<占用> / 4 格
弹药库：<占用> / 9 格
仓库：<占用> / 45 格
```

即使标题已经改名，详情舰名仍显示真实身份。占用格数按非空槽位计数，64 发弹药和一个装满的潜影盒各占一格；不递归统计容器内物品数量。详情不逐项列出库存。

详情首行直接显示真实舰名，不加“舰名：”；次行统一为 `<船型>·<舰种>·<国籍>`，例如 `大型·航母·U国`。中文中点两侧不留空格；英文使用 `<size> · <type> · <nationality>`，中点两侧各一个半角空格。国籍读取共用舰船定义，不在核心中重复保存。

熟练度以整数显示，初始为 `熟练度：0 / 200`，英文对应 `Proficiency: 0 / 200`；达到上限显示 `200 / 200`。不显示待定的增长速度、训练进度条或收益说明，未按 Shift 时本模组只追加灰色通称。

没有身份时标题回退为“未初始化舰装核心”；定义缺失时回退为“未知舰船”，保留可读取的原始 ID。非 Shift 模式仍只追加灰色通称，异常原因在 Shift 中显示，不能伪造正常属性或容量。

Shift 按键读取与颜色展示适配放在客户端路径。通用存储、属性查询及服务端入口不得直接加载 `Screen` 或其他客户端类。原版 F3+H 与第三方附加说明保持各自行为。

## 11. 掉落物保护

保护只按核心物品类型判断，适用于有效、空白及异常身份核心。核心掉落物免疫火焰、岩浆、爆炸、仙人掌等环境伤害，并且不因自然超时消失。

采用物品防火属性和伤害入口实现防护，掉落物使用无限寿命标记；标记在生成和读档后均成立，服务器重启、区块重载和跨维度后保持。拾取、漏斗收集、运动与普通容器转移继续正常执行，不为永久掉落强制加载区块。

虚空移除允许发生，不增加回收、悬停或返还背包行为。管理员删除不作为需要阻止的环境伤害。核心放入潜影盒、收纳袋等容器后，不为外层容器增加防护；允许含核心的外层容器被销毁或自然消失。

内部物品始终保存在核心组件中。核心从玩家背包正常掉落时不会把内部物品另行散落，也不添加第二份内容掉落。已装配专用舰装栏的死亡去向留待该系统设计。

## 12. 获取与制造衔接

统一工厂入口按舰名 ID 创建数量为一、身份有效、熟练度为 0、四类内容与燃料均为空的核心。创造栏、未来船坞与奖励都使用同一入口。

未带身份的普通 `/give piranport:rigging_core` 结果不自动变为可用舰船。测试需要通过工厂创建有效核心，不能把测试舰名或假数值加入生产目录。

末地城奖励箱暂缓，深海 Boss 奖励箱随世界系统后续设计。船坞未来检查对应通用舰种的具体图纸许可；每件固定消耗一张的既有规则不变，但本阶段不接入扣料、取消、耗时或产物事务。
